# Passkey + one-time PIN example

A small, single-owner web app showing passkey sign-in on iPhone and Windows. A one-time operator-issued PIN authorizes the creation of a passkey. After that, sign-in uses the passkey. There is no public signup, username, email login, password, or PIN-only everyday login.

This standalone Next.js and Better Auth example is [MIT licensed](LICENSE).

## How it works

```text
operator (app stopped) ── issues 8-digit PIN, valid 30 minutes
                                  │
browser /setup ── PIN ── single-use 10-minute registration grant
                                  │
                       device creates passkey
                                  │
browser /login ── passkey + device verification ── session cookie
```

The PIN is only for enrolling a device. It cannot sign in to the protected page by itself. Better Auth requires one fixed internal `owner` row to associate passkeys and sessions; that row has a synthetic `.invalid` email and is never used for email or account login. The app has no user-facing accounts or credentials. Up to three passkeys can be registered; an iCloud-synced passkey may already work on more than one Apple device.

## Run locally

Requires Node.js 20.9+ and npm. From this repository:

1. `npm install`
2. Copy `.env.example` to `.env` and replace `BETTER_AUTH_SECRET` with a fresh random secret of at least 32 characters. For example, `node -e "console.log(require('node:crypto').randomBytes(32).toString('base64url'))"` prints one. Keep `.env` private.
3. `npm run db:push`
4. `npm run seed`
5. While the app is **stopped**, run `npm run setup-pin -- --app-stopped`. Keep the printed PIN private.
6. `npm run dev` and open `http://localhost:3000/setup` on that computer. Enter the PIN and create a passkey.
7. Sign out, then sign in at `/login` using your passkey.

The `--app-stopped` flag is an operator assertion; the command cannot stop the app for you. Stop the server and wait for in-flight requests to finish before issuing or replacing a PIN. A second device needs a new PIN. Issuing a new PIN keeps existing passkeys. When all three slots are occupied, an operator reset is required.

## iPhone and Windows

An iPhone cannot use your computer's `localhost` address. Deploy this example to **one persistent HTTPS hostname**, set `BETTER_AUTH_URL` to that exact origin, and use a persistent SQLite volume at `DATABASE_URL`. Create the first passkey from `/setup` in Safari on the iPhone.

On Windows, open the **same HTTPS hostname** in Edge or Chrome, choose **Sign in with passkey**, then choose **iPhone, iPad, or Android device** in the Windows prompt. Scan the code displayed by Windows with the iPhone that holds the passkey and confirm on the phone. Bluetooth and a supported browser/device are needed for nearby-device authentication. You can also issue another PIN and create a separate Windows Hello passkey.

The code in that Windows prompt is part of the operating system's passkey flow, not a code generated by this app. A setup PIN alone does not make an iPhone passkey available for Windows sign-in; create the iPhone passkey first.

Changing the hostname changes the WebAuthn relying party ID. Passkeys created on `localhost` will not work on the deployed hostname, and passkeys from one deployed hostname will not work on another. Use HTTPS outside `localhost`.

## Recovery and security

If every passkey is lost, verify the owner through an established **out-of-band** process. Stop the app, then run `npm run setup-pin -- --app-stopped --reset`. This revokes passkeys, sessions, pending challenges and grants, then issues a new one-time PIN. There is intentionally no public reset endpoint.

PINs expire after 30 minutes and are stored as keyed hashes. The public PIN form uses one shared 500-attempt limit per 15 minutes; it does not trust caller-supplied IP headers. Each successful PIN exchange creates a 10-minute, one-use registration grant. Registration and authentication require device verification. Server-side passkey deletion is disabled through the public auth API. Session cookies are managed by Better Auth.

SQLite makes this example easy to run on a single persistent Node server. It is **not** a ready-made multi-instance or serverless deployment: move the database and rate limits to shared persistent storage before scaling, and keep the auth secret identical across instances. Set `BETTER_AUTH_URL` explicitly in production, store the auth secret outside Git, and back up the database. Auth routes use a fixed set of shared rate-limit buckets, including one for unknown paths. A determined visitor can still exhaust a shared limit and temporarily delay setup or sign-in; deploy edge-level abuse controls before using this pattern in production.

## Main files

| File | Role |
| --- | --- |
| `src/lib/auth.ts` | Better Auth passkey configuration and persistent rate limits |
| `src/lib/setup-pin.ts` | One-time PIN issuance, exchange and reset |
| `src/lib/passkey-policy.ts` | Requires verified device and one-use grant; caps passkeys at three |
| `src/app/actions/setup.ts` | Public PIN form action |
| `src/components/PasskeyButton.tsx` | Browser passkey registration and sign-in |
| `prisma/schema.prisma` | Internal principal, passkeys, sessions, PINs and grants |
